# 📘 Today I Learned

### 1. 오늘 배운 내용

- JPA에서 `@ManyToOne`과 `@OneToMany`를 사용해 엔티티 간 1:N 양방향 연관관계를 설정했습니다.
- `@JoinColumn(name = "member_id")`을 통해 DB의 외래 키(Foreign Key)가 `assignment` 테이블에 생성됨을 확인했습니다.
- `mappedBy = "member"`의 의미를 이해했습니다. Member는 연관관계의 주인이 아니라 읽기 전용이며, 실제 외래 키는 Assignment가 관리합니다.
- `@Transactional`을 서비스 계층에 적용하는 이유와 방법을 학습했습니다.
- 클래스 레벨에 `@Transactional(readOnly = true)`를 붙이고, 데이터를 변경하는 메서드에만 `@Transactional`을 개별적으로 붙이는 전략을 적용했습니다.

### 2. 핵심 정리 (내 언어로)

**연관관계 매핑**

JPA에서 객체 간의 관계를 표현할 때 연관관계 매핑을 사용한합니다.
이번 미션에서는 한 명의 Member가 여러 개의 Assignment를 가질 수 있는 1:N 관계를 설정했습니다.

- `@ManyToOne` : "나(Assignment)는 N쪽이다"라고 선언합니다. 외래 키를 직접 관리하는 연관관계의 주인이 됩니다.
- `@OneToMany(mappedBy = "member")` : "나(Member)는 1쪽이다"라고 선언합니다. mappedBy는 "이 관계의 외래 키는 Assignment의 member 필드가 관리한다"는 뜻으로, DB에 별도 컬럼이 생기지 않습니다.
- `@JoinColumn(name = "member_id")` : assignment 테이블에 member_id라는 외래 키 컬럼이 생성됩니다.

핵심은 **외래 키는 항상 N쪽(Assignment)에 존재**하고, JPA에서도 외래 키를 관리하는 쪽(연관관계의 주인)은 `@ManyToOne`이 붙은 Assignment라는 것입니다.

**트랜잭션**

트랜잭션은 여러 DB 작업을 하나의 단위로 묶어, 중간에 실패하면 전체를 롤백해주는 메커니즘입니다.
`@Transactional`을 서비스 계층에 적용하는 이유는 비즈니스 로직이 서비스에 있기 때문입니다.

- 클래스 레벨 `@Transactional(readOnly = true)` : 모든 메서드가 기본적으로 읽기 전용 트랜잭션으로 동작합니다. JPA의 변경 감지(dirty checking)를 수행하지 않아 성능상 이점이 있습니다.
- 메서드 레벨 `@Transactional` : 등록/수정/삭제처럼 데이터를 변경하는 메서드에만 개별적으로 붙여 읽기 전용을 해제하고 INSERT/UPDATE/DELETE가 정상 실행되도록 합니다.

### 4. 느낀 점

이번 미션에서 가장 어려웠던 부분은 연관관계의 주인 개념이었습니다.
DB에서는 외래 키 하나로 양쪽을 조인할 수 있지만, JPA 객체에서는 누가 외래 키를 관리하는지 명확히 지정해야 한다는 것이 처음에는 헷갈렸습니다.
mappedBy가 단순히 "반대편 필드 이름"을 가리키는 것이 아니라 "나는 연관관계의 주인이 아니다"를 선언하는 것임을 이해하고 나서 훨씬 명확해졌습니다.
또한 `@Transactional(readOnly = true)`를 클래스 레벨에 붙이고 변경 메서드에만 `@Transactional`을 추가하는 패턴이 실무에서 자주 쓰이는 이유를 직접 경험하면서 이해할 수 있었습니다.
단순히 어노테이션을 붙이는 것이 아니라 왜 이렇게 설계하는지 알게 된 것이 가장 큰 수확이었습니다.
