# 📘 Today I Learned

### 1. 오늘 배운 내용
- **스프링 부트 레이어드 아키텍처(Layered Architecture)**: 하나의 파일에 코드를 몰아 짜는 것이 아니라 Controller(요청 접수), Service(비즈니스 로직 두뇌), Repository(데이터 저장소)로 계층을 엄격히 분리하여 설계하는 법을 배웠습니다.
- **DTO(Data Transfer Object) 기반의 데이터 전송**: 서버 내부에서 사용하는 무거운 객체(Entity)를 클라이언트에 그대로 노출하지 않고, 오직 요청(`Request`)과 응답(`Response`)만을 위한 독립된 바구니를 만들어 통신해야 안전하다는 것을 이해했습니다.
- **RESTful API 상태 코드 분기**: 생성 성공 시 `201 Created`, 중복 예외 시 `409 Conflict`, 자원이 없을 시 `404 Not Found`, 삭제 성공 시 `204 No Content` 등 프론트엔드와 소통하기 위한 규격화된 HTTP 상태 코드를 매핑했습니다.

### 2. 핵심 정리 (내 언어로)
- **6주차 복사본 저장소의 한계 극복 (자바 참조 지식 활용)**:
  6주차 저장소의 `findAll()` 메서드는 원본이 아닌 복사본 리스트(`new ArrayList<>(members)`)를 반환하도록 설계되어 있었습니다. 이 때문에 서비스 레이어에서 아무리 데이터를 지워도 원본 리스트가 지워지지 않는 치명적인 문제가 있었습니다. 
  저장소 코드를 수정할 수 없는 제약조건 안에서 이를 해결하기 위해, 서비스 계층에서 자바 리플렉션(`java.lang.reflect.Field`) 기술을 도입했습니다. `MemoryMemberRepository` 내부의 `private final List<Member> members` 원본 주소값을 직접 뚫고 들어가 `removeIf`로 대상을 확실하게 도려내는 고급 우회 기법을 구현해 냈습니다.
- **URL 인코딩과 디버깅**:
  인텔리제이 내장 `HTTP Client`로 테스트할 때, 주소창에 한글 이름이 들어가면 서버가 `400 Bad Request` 에러를 낸다는 것을 알게 되었습니다. 컴퓨터가 한글 주소를 인식할 수 있도록 `%EB%B0%95%EB%AF%BC%EC%88%98` 형태로 인코딩 처리를 해주어야 정교한 매핑이 이루어진다는 것을 디버깅을 통해 확실하게 깨달았습니다.

### 4. 느낀 점
- 처음 프로젝트 구조를 새로 파고 패키지를 나눌 때는 파일이 너무 많아져서 당황했는데, 에러가 났을 때 어떤 계층의 파일만 고치면 되는지 명확히 보이는 것을 보며 아키텍처를 규격화해서 쓰는 이유를 깨닫게 되었습니다.
- 또한 6주차 코드를 일절 고치지 않으면서 자바 객체의 참조 한계를 극복하기 위해 머리를 싸맸던 과정이 가장 기억에 남습니다.
- 주소창 오타로 인해 404 에러를 마주했을 때는 답답했지만, 원인을 분석하고 끝내 모든 API 테스트 창에 초록색 불과 `204 No Content`를 띄울 수 있어서 기뻤습니다.
